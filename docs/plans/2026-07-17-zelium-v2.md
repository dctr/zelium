# Zelium V2 Canonical Document URLs Implementation Plan

> **For Hermes:** Implement this plan task-by-task using strict TDD. For every production-code change, write one failing test, run it and verify the expected RED failure, make the smallest implementation change, run GREEN, run the relevant suite, then commit the coherent task.

**Goal:** Give every Markdown page a stable, shareable URL of the form `/<vault-slug>/<vault-relative-path>.md`, supporting direct loads/reloads, browser history, and relative Markdown links across a multi-vault Zelium installation.

**Architecture:** Keep Zelium as a dependency-free Svelte SPA backed by the existing Fastify server. The server parses stable, URL-safe vault slugs from `VAULT_DIRS`, exposes them in `GET /api/vaults`, and returns the SPA shell for browser requests to document URLs. A focused client URL codec translates between `location.pathname` and the existing `{ rootId, path }` page selection, while a Milkdown DOM-link handler routes same-origin Markdown links through the same navigation path.

**Tech Stack:** TypeScript, Svelte 5, Vite, Fastify 5, Milkdown/ProseMirror, Vitest, Playwright. No new runtime dependency and no database or filesystem-content model change.

## Product Decisions and Acceptance Criteria

### Canonical URL contract

- A page URL is `/<vault-slug>/<vault-relative-page-path>.md`.
  - Example: `https://zelium.ai.ts.chd.sh/codex/projects/current/plan.md`.
- URL path segments must be encoded individually with `encodeURIComponent`; page paths remain vault-relative POSIX paths.
- The browser URL contains no host filesystem paths and no internal transient `root-1` IDs.
- `location.pathname === '/'` remains a valid app landing state with no page selected.
- Unsupported paths (for example, `/unknown-vault/page.md`, a path missing `.md`, or a URL with an invalid encoded segment) must produce a visible, accessible client error—not a blank editor.

### Vault configuration contract

- Preserve current syntax:

  ```bash
  VAULT_DIR=/path/to/codex
  VAULT_DIRS="/path/to/codex;/path/to/david"
  ```

- Add named multi-vault syntax:

  ```bash
  VAULT_DIRS="codex=/path/to/codex;david=/path/to/david"
  ```

- The portion before the first `=` is a stable vault slug. It is returned as both `slug` and the current sidebar `name` for named roots.
- Unnamed roots derive `slug` and `name` from `path.basename(realpath(root))`, maintaining current UI behavior.
- Accept only lowercase URL-safe slugs matching `^[a-z0-9][a-z0-9-]*$`.
- Startup must reject malformed named entries, empty names/paths, invalid slugs, duplicate real paths, and duplicate slugs. Do not auto-disambiguate, because it would make shared URLs ambiguous or unstable.
- `VAULT_DIRS` continues to take precedence over `VAULT_DIR`.
- Internal API requests continue to use `rootId`; add `slug` only to the public vault list payload. This avoids a wider API migration in V2.

### Navigation behavior

- Loading or reloading a valid page URL fetches and displays that document.
- Selecting a page in the sidebar uses `history.pushState` to set its canonical URL before/while loading it.
- Back/forward navigation (`popstate`) loads the page represented by the current pathname without pushing another history entry.
- Same-origin Markdown links that resolve to a canonical Zelium `.md` URL navigate in-app:
  - `[page2](../page2.md)` from `/codex/folder/page1.md` becomes `/codex/page2.md`.
  - Absolute internal links such as `/david/notes/page.md` can cross vaults.
  - Hash-only links, external links, non-`.md` links, download links, modifier-clicks, middle-clicks, and links with `target` are left to normal browser behavior.
- Links to paths that are syntactically document-shaped but do not exist are routed in-app and show the existing API error (normally 404) in the workspace.

### Server fallback and safety behavior

- `/api` and `/api/*` never receive the SPA fallback.
- Existing built assets always win over SPA fallback.
- Normal browser navigations (`Accept: text/html` or `*/*`) to a URL ending in `.md` receive `index.html`; this includes nested document routes.
- Requests for unknown non-document files still return 404 rather than HTML. Preserve asset traversal protections.
- Do not map document URLs directly to vault files from static serving. The only filesystem page access remains via the path-validated vault API.

## Risks, Trade-offs, and Non-goals

- **Stable-slug risk:** Changing a slug breaks every previously shared URL. The documentation must call this out; V2 deliberately does not add redirect aliases, persistent route history, or a hidden metadata store.
- **Rename/move risk:** Renaming/moving a Markdown file changes its URL. V2 does not provide redirects because the application stores only Markdown and has no link-alias layer. This is consistent with direct file-path URLs but should be revisited if link durability across moves becomes a product requirement.
- **Slug/display-name trade-off:** V2 makes an explicit slug also the displayed vault name. Separating `slug` from an optional human label is deferred until there is a concrete need; introducing a third configuration field now would make the environment grammar and migration surface larger.
- **Hash anchors:** V2 guarantees document selection and routing, not restoration of heading scroll positions for `#fragment` links. Preserve ordinary same-document anchor behavior; add cross-document anchor restoration only with dedicated acceptance tests.
- **No router library:** A small pure codec plus `history` API is sufficient for one canonical route form. Adding a general router would increase dependency and migration complexity without providing material value.
- **Security boundary:** Client route validation improves UX only. The existing server `resolveVaultPath` checks remain mandatory and authoritative for every page read/write. Static deep-link fallback must never read vault files directly.
- **Deployment:** This plan changes source and tests only. Updating the live process environment, rebuilding, restarting the service, and testing the public host are external side effects requiring separate approval.
